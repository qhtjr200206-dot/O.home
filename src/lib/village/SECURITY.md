# 마을(웹게임) 보안 설계 — 구현 기준

구현: `server.ts`(로직, Firestore 주입), `firebase.ts`(Admin SDK 연결·HTTP·조회 속도 제한), `games.ts`(미니게임 규칙·서버 재생),
`src/app/api/village/route.ts`. 시험: `node scripts/run-village-emulator.cjs`(Firestore·Auth 에뮬레이터, demo 프로젝트),
`node scripts/test-village-games.cjs`, `node scripts/test-village-map.cjs`, `node scripts/test-village-password.cjs`.

## 저장 위치와 직접 접근

- `village_rooms/{roomId}`(방·scrypt 해시·인스턴스·비밀번호 버전·캐릭터 원본 식별), 하위 `pos`·`events`·`scores`·`limits`·`games`,
  `village_owner_slots/{uid}`, `village_join_tries/{hash}`, `village_cleanup/{roomId}` — 모두 Admin SDK(서버) 전용.
- 운영 규칙(`firebase/firestore.production.rules`)과 설치 규칙(`firebase/firestore.rules`)은 목록에 없는 컬렉션을
  아무에게도 열지 않는다. 규칙을 바꾸지 않고도 클라이언트 직접 읽기·쓰기가 거부된다(에뮬레이터에서 두 규칙 파일 그대로 검증,
  운영에서는 비로그인 REST 읽기 403 PERMISSION_DENIED 확인).
- 운영 서버는 요청 처리 전에 배포된 규칙이 위 두 파일 중 하나와 같은지 Firebase Rules API(읽기 전용)로 확인하고,
  다르거나 확인할 수 없으면 503으로 닫힌다(10분 캐시). 운영 환경에 에뮬레이터 변수가 있으면 503.

## 인증과 방 세션

- 로그인: Firebase ID 토큰을 `verifyIdToken(token, true)`로 검증. 요청 본문의 uid·관리자 여부는 받지 않는다.
- 관리자: 매 명령마다 `meta/owner`의 `uid`/`admins`를 다시 읽는다(규칙의 isAdmin과 같은 기준).
- 방 입장은 로그인 필수. 비밀번호 검사 '전에' 계정+방 단위 시도를 트랜잭션으로 예약한다(15분당 8회). 맞으면 예약을 돌려준다.
- 방 전체 실패 수는 정답 입장을 막지 않는다(누구나 방을 잠그는 DoS 방지). 15분 안에 방 전체 실패가 24회를 넘으면 보호 모드:
  계정당 허용 2회, 가입한 지 24시간이 안 된 계정은 검사 전에 거절(다계정 대입 완화). 방 주인·관리자는 시도 제한 예외.
- 방 비밀번호: 8~64자, 같은 글자 반복·숫자만 9자 이하·흔한 비밀번호 거부. 현재와 같은 비밀번호로의 변경 거부(자동 완성으로 모두가
  쫓겨나는 사고 방지). scrypt(N=16384, r=8, p=1, 16B salt) + timingSafeEqual.
- 세션 토큰: HMAC-SHA256(`VILLAGE_SESSION_SECRET` 또는 서비스 계정 비공개 키에서 파생) 서명, 12시간 만료,
  `방 id·인스턴스·비밀번호 버전·발급 사용자`에 묶인다. 모든 요청이 최신 방 문서와 대조하므로 방 삭제·비밀번호 변경 즉시 무효,
  다른 계정·비로그인으로 옮겨 쓸 수 없다.

## 방 생성·삭제 정책(사용자 확정)

- 가입자는 동시에 1개, 관리자는 무제한. 생성 트랜잭션이 관리자 여부·자관·캐릭터 열람 권한·보유 방(쿼리)·슬롯 문서를 함께 읽고
  슬롯을 항상 쓴다 → 같은 사용자의 동시 생성·삭제와 권한 변경이 직렬화된다. 강등된 관리자는 보유 방이 0개가 될 때까지 새로 만들 수 없다.
- 삭제는 방 주인 또는 관리자만. 방 문서 삭제와 슬롯 감소가 한 트랜잭션이라 삭제 직후 바로 재생성할 수 있다.
  하위 데이터·시도 기록은 이어서 지우고, 실패하면 `village_cleanup` 대기 문서를 남겨 503 → 같은 삭제 요청으로 재시도.

## 캐릭터 연결과 조작 권한

- 방을 만들 때 각 캐릭터 문서의 생성 시각(createTime, 서버가 정함)을 기록한다. 표시·조작은 지금 문서가 같은 문서이고 방 주인이
  여전히 볼 수 있을 때만 인정한다 → 삭제된 id를 남이 다시 만들어 사칭할 수 없고, 비공개로 바뀐 캐릭터는 방에서 사라진다.
- 방 화면의 이름·색·도트는 매 조회 때 원본 캐릭터 문서에서 다시 읽는다(4초 캐시). 잠긴 캐릭터는 도트를 내보내지 않는다.
- 조작 권한: 관리자, 캐릭터 문서의 `authorId`, `data.grants`의 play/edit(잠금 캐릭터는 `char_secrets`의 원본 grants).
  NPC는 방 주인·관리자. 매 명령마다 트랜잭션 안에서 다시 읽으므로 권한 회수가 즉시 반영된다.
- 기존 규칙은 캐릭터 생성 때 `authorId` 값을 검사하지 않는다(사이트 기존 규칙 문제). 남의 명의로 만든 문서로는 그 명의자만 조작권을
  얻으므로 위조자에게 이득이 없고, 기존 캐릭터의 방 안 권한은 createTime 비교로 보호된다(에뮬레이터 시험).

## 행동 검증

- 이동: 서버가 같은 시드로 맵을 다시 만들어 걸을 수 있는 칸인지 확인. 선물은 방 시대 품목만, 받는 캐릭터는 지금 보이는 배우만,
  메시지 300자·제어/양방향 문자 제거. 분당 이동 90·대화 12·게임 20회(트랜잭션).
- 미니게임: 클라이언트는 점수를 보내지 않는다. `gameStart`로 서버가 시드와 시작 시각을 기록하고, 끝나면 입력(별 줍기 400틱의
  바구니 위치, 짝 맞추기 뒤집은 순서)을 보내 서버가 같은 규칙으로 재생·계산한다. 한 판은 시작한 사람·캐릭터만 한 번 제출,
  15분 만료, 별 줍기는 20초 전 제출 거부, 짝 맞추기는 사람이 불가능한 속도 거부.
- 응답에는 비밀번호 해시·작성자 uid·방 주인 uid를 넣지 않는다.
- 조회(list·state·controls·join) 요청은 서버 인스턴스 메모리에서 계정(비로그인은 Vercel 접속 주소)별 분당 상한을 둔다.

## 남은 한계(의도·수용)

- 자동화 봇이 사람처럼 플레이하는 것은 클라이언트 게임 특성상 완전히 막을 수 없다(임의 점수 신고는 불가).
- 조회 속도 제한은 서버 인스턴스별이다(여러 인스턴스에 분산되면 상한이 그만큼 커진다).
- 방 목록에는 이름·시대만 공개된다(로그인 없이도). 내용은 비밀번호 입장 후에만.
- Supabase 연결에서는 마을을 열지 않는다(서버가 503, 화면은 안내만).
- `village_join_tries`에는 `expireAt` 필드가 있다. 운영 Firestore TTL 정책을 켜면 만료 문서가 자동 삭제된다(오너 선택 사항).
