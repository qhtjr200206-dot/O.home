# 마을 서버 독립 검토 (미완성, 출시 금지)

이 검토는 기존 작업과 분리된 세션에서 코드와 로컬 규칙 파일을 읽어 수행했다. 운영 규칙이나 데이터는 조회·변경하지 않았으며 실제 운영 보안 상태를 확인한 것이 아니다.

## 발견과 차단 요건

- `src/lib/firebaseRules.ts` 81–95행의 제안 규칙은 로그인 사용자의 콘텐츠 생성과 작성자·`editorIds`의 문서 전체 변경을 허용한다. `characters`도 콘텐츠에 포함되며 `grants` 및 `editorIds`에 대한 필드별 불변 제약이 보이지 않는다. 따라서 게임 서버는 이 필드를 신뢰할 수 있는 권한 원본으로 가정하면 안 된다. 허용되는 수정 범위와 권한 변경 주체를 백엔드 양쪽에서 격리 테스트하고, 신뢰 가능한 별도 권한 원본 또는 안전한 규칙이 필요하다. 작성자가 직접 권한을 부여할 수 있어야 하는지 정책도 정해야 한다.
- `firebase/firestore.rules`는 editorIds 허용 여부 등에서 위 제안 규칙과 다르다. 실제 배포 규칙은 미확인이다. 하나를 실제 규칙이라고 단정하거나 규칙 미적용 환경에서 게임을 노출하지 않는다.
- 일반 사용자의 활성방 제한은 읽고 쓰는 별도 작업이 아니라 사용자 슬롯과 방 생성을 같은 DB 트랜잭션에서 처리해야 한다. 관리자 판정은 트랜잭션과 호환되는 신뢰 가능한 서버 권한 원본을 사용해야 한다. 관리자가 일반 사용자로 강등되어 여러 방을 이미 가진 경우의 해소 정책은 미결이다.
- 삭제는 권한 검증 후 해당 인스턴스의 `deleting` 전환 및 세션 무효화, 인스턴스에 한정된 재시도 가능 정리, 완료 시 슬롯 해제가 필요하다. 일반 사용자의 새 방 생성은 정리 완료 전 거부한다. 삭제·쓰기 경합은 실제 저장소 트랜잭션으로 검증해야 한다.
- 기존 권한은 `Character.grants`의 play/edit이며 edit는 play를 포함한다. 방 소속과 동일 캐릭터의 현재 권한을 매 명령 확인하되, 위 권한 원본 신뢰성 문제를 먼저 해결해야 한다. 비공개 캐릭터·자관의 원본 데이터 및 공개 이미지 주소를 방에 복제할 때 원래 접근 정책을 우회하지 않도록 별도 설계가 필요하다.
- 방 비밀번호 해시는 서버 전용만으로 충분하지 않다. 공유·원자적 시도 제한, 사용자/방별 제한과 자원 고갈 방지, 세션 서명·만료·폐기, 서버 측 저장 및 직접 접근 거부, 토큰 검증이 필수다. Firebase 에뮬레이터와 격리된 Supabase에서 직접 접근·경합·권한 회수 및 실패 주입을 각각 재현해야 한다.

## 이번 격리 구현

`src/lib/village/password.ts`는 외부 의존성 없는 Node scrypt 기반 고정 파라미터 버전 형식, 무작위 16바이트 salt, 고정 길이 해시 비교와 입력 크기 제한을 제공한다. 이는 아직 라우트·DB에 연결되지 않았고 독립 암호 리뷰 및 실제 부하에서 파라미터 확인도 받지 않았다. 형식 오류는 즉시 거부하므로 응답 시간의 균일성을 보장하지 않는다. 잘못된 기록 검출·사용자 열거를 포함한 응답 및 로깅 정책을 연결 전에 설계해야 한다. 비밀번호 강도 정책과 시도 제한은 구현하지 않았다. Next.js 로컬 인증 가이드가 강조하는 인증·세션·인가 분리를 따르되, 이 함수는 그 어느 것도 대체하지 않는다.
